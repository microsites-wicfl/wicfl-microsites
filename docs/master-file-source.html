Objective

Build a network of highly targeted insurance microsites for WICFL, starting in the Stuart and Treasure Coast market and expanding south through Palm Beach, Broward and Miami. Sites will be lightweight, fast, SEO focused, and built in both English and Spanish.

The long term target is 100 or more sites. That target is not what we are building right now.

Guiding principle

The objective at the beginning is not to build websites quickly. It is to build the factory that lets us build websites quickly and consistently later. We want to avoid reaching Site #20 and discovering we have twenty individually managed websites.

Two things follow from that principle, and they shape everything below. First, the factory gets built before the sites, not extracted from them afterward. Second, we prove the factory works and prove the sites produce business as two separate questions, because they resolve on completely different timelines.

The risk this scope exists to manage

Google's published spam policy names our exact pattern under doorway abuse: “Having multiple domain names or pages targeted at specific regions or cities that funnel users to one page.” Their June 2026 spam update enforced this against local and home services businesses. Separately, 100 new domains means 100 sites with no authority, no backlinks and no reviews, which is what actually decides local rankings.

Building three sites and measuring is cheap. Building a hundred and being wrong is a year and a six figure content bill.

Decisions and why

Settled decisions with the reasoning attached, so we do not relitigate them in six months without remembering why.

DecisionChoiceReasoning
Hosting Cloudflare Workers with Static Assets Cloudflare Pages still works but no longer receives new platform features and caps at 100 projects per account, which is a wall at exactly our target scale. Same cost, no ceiling, and it is where Cloudflare is investing.
Framework Astro At 100 sites averaging 30 pages, plain HTML is 3,000 hand maintained files. Astro gives content collections, native English and Spanish routing, zero JavaScript by default, and a build driven entirely by config files.
Repositories One monorepo With 100 repos, one template fix becomes 100 pull requests and 100 dependency streams. That is the same trap as 100 WordPress installs.
Domains Cloudflare Registrar Sold at cost with no markup, free WHOIS redaction, and a registration API so provisioning can be scripted. Keeps domains, DNS, SSL and hosting in one place.
Grouping at scale Pods of about 25 sites per Worker One Worker per site caps us at 500 and multiplies deploys. One Worker for everything means a bad deploy takes down the whole portfolio.
Niche selection SEO validation before any domain is bought Added from Pavel's research. Kevin selecting a niche is not the same as the niche being winnable. If a market is owned by national aggregators with no real local angle, keyword and SERP analysis tells us in days rather than at Gate B four months later.
Generator timing Minimal generator from Site #1, heavy automation after Site #3 The Phase 2 generator is deliberately crude and gets rewritten during the pilots. If Site #1 is hand assembled there is no config driven path to improve, and Gate A stops meaning anything. Domain and provisioning automation do wait until after Site #3.
Operator profile Config and markdown only The person launching sites never writes HTML and never edits components to ship one. They diagnose, they do not build. This is a hard framework requirement, not a preference.
Advancement Two separate gates Technical repeatability and commercial validity are different questions on different clocks. Collapsing them is how a team ships twenty sites that deploy beautifully and generate nothing.
Site #3 Generated, not hand built If all three sites are assembled by hand, #3 is faster because Pavel has done it twice. That measures Pavel's learning curve, not the factory.

Architecture

How a site comes into existence

Repository layout

├── sites/
│   ├── stuart-flood/

├── scripts/               new-site, provisioning, differentiation check
└── .github/workflows/     path filtered builds, only changed sites rebuild

Launching a site never means writing HTML. It means running new-site, filling in the config, and writing markdown. Template code is touched only when improving the framework for every site at once. If anyone finds themselves writing HTML for a single site, that is a defect in the framework and it gets fixed there.

What the framework provides out of the box

Bilingual routing
English and Spanish paths with correct hreflang, built in from Site #2 rather than retrofitted later
Technical SEO
Sitemap, robots, canonical tags, and schema.org markup for an insurance agency, generated from config
Analytics
GA4 and GTM wired identically on every site, so cross site reporting works without per site cleanup
Lead capture
Forms routed into the existing CRM, with the originating site recorded on every lead
Call tracking
The tracking number is a config field, rendered everywhere it appears, routed into the existing GoTo system
Performance
Zero JavaScript by default. Core Web Vitals are a build output, not a per site optimization project

Why differentiation is a required field

It forces every site to declare, in writing, what makes it different from every other site before it can be generated. A site that cannot fill this in is a site that should not be built.

Content standards

The swap test

Take any page. Swap the city name for a different city. What else on the page has to change? If the answer is nothing, that page is a doorway page by Google's definition and it does not ship, regardless of how well the site is built.

This is not a matter of discipline. The CI differentiation gate compares content across every site in the portfolio and blocks the deploy when two pages are too similar. It costs a day to build and it protects the portfolio permanently, including from a future team member who was never in this conversation.

Standing rules

  • Spanish is written, never translated. Machine translated insurance copy reads as inauthentic to the Miami and Broward market immediately, and it falls under Google's scaled content policies. Spanish sites need a native writer.
  • Local proof is required, not optional. Real claims handled, area specific detail, local reviews, genuine knowledge of the market. This is the raw material the swap test is looking for.
  • Florida insurance advertising rules apply on every page. License number displayed, no misleading coverage claims, correct entity naming. Encoded in the template so it cannot be forgotten per site.
  • NAP consistency. Name, address and phone must match the Google Business Profile exactly. Inconsistency actively suppresses local rankings.
  • No AI generated content shipped unreviewed. See below.

How AI may and may not be used

Allowed: drafting from a brief, restructuring, tightening, generating outlines, research support, and first passes that a human then edits into something true.

Not allowed: publishing anything without a human editing pass. Generating a site's content from a template brief and shipping it. Producing Spanish content by translating or generating from an English brief.

Why the line sits here and not somewhere more convenient: Google's scaled content abuse policy covers pages generated at volume to rank rather than to help, and it applies explicitly “no matter how it's created.” Combined with the doorway pattern our portfolio structurally resembles, a hundred sites of brief driven generated copy is the exact profile enforcement looks for. The mechanism is what gets caught, not the intent behind it.

Phase 2 is split by real deadline, not trimmed

Ten items in nine working days does not fit, especially with Pavel shadowing, which costs velocity rather than adding it. The fix is not cutting scope, it is noticing that only half of Phase 2 is actually gated by the 18 September handoff.

Block A, due 18 September: config schema, Astro template, bilingual routing, the minimal generator, and the handoff session. Without these Pavel cannot start Site #1 on 21 September.

Block B, due 9 October: full technical SEO, tracking number wiring, analytics and CRM capture, the CI differentiation gate, and the QA checklist. These are gated by Site #1's launch and get built during Phase 3 with Pavel already operating. If one overruns it slides inside October without touching the 21 September start.

One caveat that keeps this honest: the CI differentiation gate must exist before the first content publishes, which is early October, not before the handoff. It is the guardrail the whole portfolio depends on.

What confirming availability did not solve

Pavel now holds three roles at once: project lead, SEO lead and content owner. That is workable across three pilot sites, roughly 50 to 75 pages. At twenty sites it becomes 400 to 500 pages on top of everything else, and content turns into the bottleneck. The failure mode is not lateness, it is thinner content, which is precisely what the spam policies penalize. The role gets revisited at Gate B, and that conversation should be expected rather than arrive as a surprise.

A related gap opened on 25 August: nobody reviews the content before it publishes. Pavel writes it, optimizes it and ships it. For insurance copy that also means nobody at Walker is checking coverage claims, disclosures and Florida advertising compliance. One review per site by someone who actually sells insurance is not a bottleneck, but it needs a name on it.

The two gates

The single most important structural decision in this plan. Advancement runs on evidence, not on elapsed time.

GateQuestionDatePass criterionIf it fails
Gate A
Technical		 Does the factory work? 13 Nov 26 Factory time of 2 working days or fewer, measured from approved content and a filled config in hand, to a live site that passes QA, with zero code written by Victor. Total elapsed time including research and writing is logged as an informational second clock. Pavel picks the niche himself. Return to Phase 5. The framework is not repeatable yet, and building more sites would only multiply manual work.
Gate B
Commercial		 Do the sites produce business? 5 Mar 27 Sites #1 and #2 hit the qualified call target defined in activity 0.7, each measured 120 days after its own launch. Do not scale. Either the niche selection was wrong and we retest, or the microsite model does not work for this market.

Why Gate A excludes the writing, and why Gate B moved

Gate A originally said "five working days," which never specified whether writing the content counted inside them. If it counts, nobody passes: 15 to 25 pages of original insurance copy takes longer than that. If it does not count, five days is far too generous and the gate measures almost nothing. Splitting it into factory time and elapsed time isolates the variable actually under test, and tightens the bar rather than loosening it.

Gate B moved from 12 February to the week of 1 March. The gate promises 120 days of data on both pilots, but Site #2 launches 30 October and its 120 days land on 27 February, fifteen days after the original date. Rather than quietly evaluate Site #2 at 105 days, the gate moves. Two and a half weeks against a four month wait is noise. Deciding to build twenty sites on thinner data than we promised ourselves is not.

Gate B has no number yet

Activity 0.7 exists to set it. The bar has to be defined now, while there is no data, because that is the only moment it can be set honestly. Set afterward, it becomes whatever the results happen to say.

Tracking numbers, resolved 25 Aug 2026

GoTo confirmed $0.99 per standard phone number, which is $1,188 a year at 100 numbers. That comes in below the forwarding alternative we had costed near $1,900, and it is operationally simpler because the numbers live natively in the phone system the team already uses. Decision: buy tracking numbers directly from GoTo.

Worth noting why we held for the written quote. Third party comparison sites put GoTo's additional numbers at $4.99 to $14.99 each per month, projecting to $6,000 to $18,000 a year at 100 numbers. The real figure is roughly a fifth of the bottom of that range. Planning against published comparisons would have over budgeted this line by up to $15,000 a year, or killed the hundred site scenario on a constraint that does not exist.

One item still to confirm: that the $0.99 is monthly and that inbound minutes are not billed separately as volume grows.

Glossary

Plain language for the terms that appear throughout this document.

Static site
A website whose pages are pre-built as files rather than assembled on every visit. Faster, cheaper and far harder to break than WordPress
Astro
The framework that turns our template plus a site's content into those pre-built pages
Monorepo
One code repository holding the shared template and every site, so a fix applies everywhere at once
Worker
Cloudflare's unit of hosting. One Worker serves a pod of roughly 25 sites
Zone
A domain as Cloudflare tracks it, carrying its DNS records and SSL certificate
CI gate
An automatic check that runs before a site goes live and blocks it if the check fails
Doorway page
A page that exists to capture a search rather than to help the person who lands on it. Explicitly against Google's policies
hreflang
The markup that tells Google which pages are the English and Spanish versions of each other
Core Web Vitals
Google's page speed and stability measurements, which factor into rankings
DID
A direct phone number. One per microsite, so every call can be traced to the site that produced it
